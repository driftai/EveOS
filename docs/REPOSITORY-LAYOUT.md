# EveOS repository layout and durability contract

EveOS treats Git as the durable product definition. A workstation checkout may accumulate caches, logs, browser state, evidence, user libraries, and installed dependencies, but those are reconstructible or private runtime state rather than source.

The rule is simple: **if EveOS needs a file in order to rebuild, test, diagnose, or qualify the product on a new clone, that file belongs in a tracked source/tooling path. If a file is generated by running EveOS or a test, it belongs in an ignored runtime/output path.**

## Durable tracked roots

| Path | Purpose |
| --- | --- |
| `config/` | Canonical configuration and schemas. `config/eveos-ports.json` is the port source of truth. |
| `css/` | First-party styles. |
| `js/` | First-party browser/runtime modules. |
| `server/` | Primary server entrypoints and service code. |
| `server_modules/` | Reusable backend/service modules. |
| `tools/smoke/` | Registered smoke tests and smoke helpers. |
| `tools/qualification/` | Durable opt-in live/machine acceptance drivers. Generated evidence does not live here. |
| `tools/audit/` | Repository, registry, generated-asset, privacy, and automation guardrails. |
| `tools/setup/` | Fresh-clone bootstrap, doctor, environment wrappers, local hygiene, and canonical verification. |
| `tests/` | Deterministic regression/contract tests. |
| `docs/` | Durable operating, reconstruction, architecture, and qualification documentation. |
| `.github/workflows/` | Minimal-permission, pinned CI automation only. |

The repository root is intentionally a small launch/metadata surface: `EveOS.html`, `audioflix-spotify-engine.html`, `start-server.bat`, package/requirements manifests, README, license, and repository metadata. New feature modules, tests, scripts, or generated logs should not accumulate at the root.

## Local/private/generated roots

These are intentionally ignored and must not become the only copy of reusable test or product logic:

| Path | Contents |
| --- | --- |
| `data/runtime/` | Machine/session runtime state and generated qualification evidence. |
| `data/modular-state/` | Local user/application state. |
| `logs/` | Generated logs. New code should prefer this over writing `*.log` at repository root. |
| `output/` | Generated exports/output. |
| `test-results/` | Generated test artifacts. |
| `playwright-report/` | Generated Playwright reports. |
| `node_modules/` | Reconstructed by `npm ci`. |
| `.venv/` | Reconstructed by the EveOS bootstrap. |
| `.pytest_cache/`, `__pycache__/` | Disposable test/interpreter caches. |
| browser/session/profile directories | Authentication/session material and machine state; never source fixtures. |

A file can be important without being safe to commit. Credentials, cookies, browser profiles, user databases, private media/library state, approval tokens, and generated evidence stay local. Track the code that can recreate or inspect them, not the populated state.

## Test and qualification placement

Reusable verification logic must be promoted out of ignored locations.

- Deterministic smoke entrypoint: `tools/smoke/` and registered through the smoke registry.
- Deterministic regression/contract test: `tests/`.
- Live, signed-in, headed-browser, or machine-specific acceptance driver: `tools/qualification/`.
- Structural/security/repository invariant: `tools/audit/`.
- Fresh-install/environment verification: `tools/setup/`.
- Generated JSON, screenshots, traces, timing samples, and failure evidence: ignored runtime/output paths.

The former Lane 3 `data/runtime/smoke-results/*.mjs` pattern is explicitly retired. The canonical Lane 3 drivers are tracked under `tools/qualification/`; only their generated evidence remains in `data/runtime/smoke-results/`.

Run the local workspace audit to detect stale reusable source left in ignored runtime evidence:

```powershell
node tools/setup/eveos_local_hygiene.mjs
```

Known promoted Lane 3 duplicates can be removed without touching evidence:

```powershell
node tools/setup/eveos_local_hygiene.mjs --prune-promoted
```

Unknown scripts are never deleted automatically. Review and promote them first if they still carry unique capability.

## Fresh-clone proof

After cloning or pulling structural/setup changes:

```powershell
node tools/setup/eveos_bootstrap.mjs
node tools/setup/eveos_verify.mjs
```

`eveos_verify` closes the repository hygiene boundary, GitHub Actions security policy, Queue View pointer-stability regression, recovered structural regression contracts, and the existing deterministic guardrail suite.

The Windows launcher and companion batch files prefer the project `.venv`, so the environment created by the bootstrap is the canonical Python runtime for EveOS launchers and verification wrappers.

## Automation security

Repository automation is treated as code with privilege boundaries:

- GitHub Actions must use explicit read-only repository permissions unless the security policy is deliberately revised.
- Marketplace actions must be pinned to immutable commit SHAs.
- Checkout credentials must not persist in the job workspace.
- `pull_request_target` is rejected by default.
- Repository guardrails do not consume project/provider secrets.
- Pipe-to-shell network execution is forbidden in tracked workflows.

`tools/audit/github_actions_security_guard.mjs` enforces this baseline and is itself part of canonical verification.

## Change rule

When adding a capability, ask two questions before committing:

1. **Would a clean clone lose an important ability if this file disappeared?** If yes, move the reusable logic into a tracked durable path.
2. **Could committing this file expose user, machine, credential, session, or generated runtime state?** If yes, keep the state ignored and track only schemas/examples/tools required to recreate or inspect it.

This keeps GitHub pull/clone as the normal transport for EveOS code and test capability instead of manual file replacement.
